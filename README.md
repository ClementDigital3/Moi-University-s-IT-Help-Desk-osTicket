# Context-Aware ML for ICT Help Desk Ticket Management

Code and results for the MSc thesis *A Context-Aware Machine Learning Based Model
for ICT Help Desk Tickets Management: A Case Study of Moi University*
(Eliud Tuwei, Moi University).

The study compares two ways of serving the three help desk decisions:

- **Arm A — one end-to-end model.** `models/end_to_end/` — one shared TF-IDF
  representation, five classifiers combined by vote, lexical retrieval.
- **Arm B — three dedicated context-aware models.** `models/classification/`,
  `models/routing/`, `models/recommendation/` — each represented and tuned
  independently, with routing cascaded on classification.

Both arms train on the same partition and are evaluated on the same held-out
partition, so every comparison is paired and McNemar's exact test applies.

## Layout

```
shared/          data, representations, context blocks, heads, metrics, artifact contract
models/
  end_to_end/    Arm A — the integrated baseline
  classification/  Model 1 (B1) — category            ← head of the cascade
  routing/         Model 2 (B2) — resolver team       ← consumes model 1
  recommendation/  Model 3 (B3) — prior resolutions   ← consumes model 1
analysis/        preprocessing, cross-cutting studies, comparison, figures, chapters
tools/           corpus generator, offline wheel fetchers
archive/         the pre-split monolithic scripts, kept for reference
```

Each model folder has its own README: what it does, how to run it, its current
result, and where to extend it. **Start there.**

### How the models stay independent

Each model reads `data/processed/` plus the published artifacts of the models
upstream of it, and publishes exactly one artifact of its own to
`results/artifacts/`. Nothing imports another model. You can rewrite the routing
model from scratch and the classification model neither knows nor cares, as long
as the artifact contract in `shared/artifacts.py` holds.

`analysis/assemble_tables.py` stitches the per-model fragments into the numbered
Chapter Four tables, so no model needs to know what the others produced.

## Data provenance — read this first

`data/raw/osticket_export.csv` is **synthetic**, generated by
`tools/generate_dataset.py` to the field specification of Table 3.1 / Appendix
II. It stands in for the authorised institutional export pending the data-access
approval described in Sections 1.10 and 3.16.

The corpus deliberately reproduces the conditions the study is about: symptom
vocabulary shared across unrelated categories, disambiguating detail that users
supply only sometimes, and compositional rather than templated phrasing. The
comparative and methodological findings are therefore informative, but **the
absolute numbers are properties of this corpus and are not measured performance
of the Moi University help desk.** Chapter Four states this.

To swap in the real export: replace `data/raw/osticket_export.csv` (same
columns), supply `data/raw/ground_truth_problem_ids.csv`, and re-run the
pipeline. Every table, figure and chapter number regenerates.

## Pipeline

```bash
# 0. corpus (skip when using the authorised export)
.venv/bin/python tools/generate_dataset.py

# 1. screening, cleaning, the one shared train/test split
.venv/bin/python -m analysis.preprocess

# 2. the models — 1 must precede 2 and 3; end_to_end is independent of all three
.venv/bin/python -m models.end_to_end.run
.venv/bin/python -m models.classification.run
.venv/bin/python -m models.routing.run
.venv/bin/python -m models.recommendation.run

# 3. cross-cutting analysis
.venv/bin/python -m analysis.assemble_tables
.venv/bin/python -m analysis.representation
.venv/bin/python -m analysis.compare
.venv/bin/python -m analysis.figures

# 4. write Chapters Four and Five into docs/
.venv/bin/python -m analysis.write_chapters
```

### Caching

Expensive intermediates live in `results/cache/` so a re-run costs seconds:

| File | Holds | Delete to |
|---|---|---|
| `emb_auto.npz` | sentence embeddings for the whole corpus | re-encode (~135 s) |
| `heads_*.json` | per-task head-selection CV scores | re-select heads (~25 min/task) |
| `probas_*.npz` | the end-to-end model's fitted branches | refit Arm A |

Head selection writes each candidate's score the moment it is computed, so an
interrupted run resumes instead of repeating hours of fitting.

## Headline results

| Decision | Arm A (end-to-end) | Arm B (task-specific) | Winner | p |
|---|---|---|---|---|
| Ticket classification | 0.9009 macro F1 | 0.8793 | Arm A | 0.00032 |
| Resolver routing | 0.6958 macro F1 | 0.6888 | Arm A | 0.03558 |
| Resolution recommendation | 0.9036 MRR | 0.9183 | Arm B | 0.00011 |

A split verdict. The cheap lexical ensemble wins the classification decisions;
semantic representation wins retrieval. Neither architecture dominates — which
is exactly what Section 3.11 asked to be tested rather than assumed.

## Prototypes

Each model gets a runnable demo for the defence. The first is finished:

```bash
.venv/bin/python -m models.end_to_end.export     # once, ~90 s
.venv/bin/python -m models.end_to_end.serve      # http://127.0.0.1:8000/
```

Self-contained — Python standard library only, no web framework, no CDN, no
network. Type a ticket, see the category and team with confidence, watch each of
the five branches vote, and read the resolutions of the most similar past
tickets. See `models/end_to_end/README.md` for what to demonstrate and in what
order.

**Evidence dashboard** — reachable two ways, whichever suits the moment:

- **From the prototype**, via the switcher in the top-left: `http://127.0.0.1:8000/dashboard`.
  Use this in a presentation so you never leave the browser.
- **As a standalone file**, `results/dashboard.html` — one self-contained file, no
  server, no CDN, no network. Double-click it, carry it on a USB stick, or email it
  to a supervisor. (The switcher hides itself here, since there is no server to
  switch back to.) It presents the Chapter Four findings interactively
(headline comparison, ablation, representation test, model candidates, Top-K
curves, routing confusion, operational comparison), with a data table behind
every chart and a dark-mode toggle.

```bash
.venv/bin/python -m analysis.build_dashboard
xdg-open results/dashboard.html
```

## Output

- `results/tables/` — every numbered Chapter Four table, as CSV
- `results/figures/` — Figures 4.1–4.7 at 300 dpi
- `results/artifacts/` — per-model published outputs and the inter-model handoff
- `results/predictions/` — paired held-out predictions for the significance tests
- `docs/MSc Thesis - ICT Help Desk Ticket Management (complete).docx`

`analysis/write_chapters.py` reads the numbers out of `results/` and writes them
into the document, so the prose cannot drift from the experiments. The source
document in `~/Downloads` is opened read-only and never modified.

## Environment

Python 3.12 with the virtualenv in `.venv`. Wheels are vendored in `wheels/`:

```bash
.venv/bin/pip install --no-index --find-links=wheels \
    scikit-learn xgboost pandas matplotlib sentence-transformers python-docx
```

Arm B uses `sentence-transformers/all-MiniLM-L6-v2`, falling back to TF-IDF →
truncated SVD where no encoder can be provisioned (the allowance in Sections 1.9
and 3.11). The encoder actually used is recorded in each model's artifact and
reported in Chapter Four.
